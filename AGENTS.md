## Coding
- Do not bring any unnecessary *possibilies* or *world-line* into the program.
  - Languages whose type systems distinguish between nullable and non-nullable types: Do not include `null`, `undefined`, or any equivalent in a function parameter's type unless there is an actual case where the argument can take such a value.
  - Every conditional branch must arise out of necessity. This is similar to satisfying the compiler when handling a `Result` type in Rust. Do not add conditional branches just to guard against exceptions that may or may not occur. If you find yourself needing to, that suggests code has been written in violation of the rule above.
- Minimize the responsibilities each function takes on.
  - A function must not have hidden side effects that cannnot be inferred from its name.
  - An unusually long function name, or one that suggests multiple responsibilities, is a code smell.
- Minimize the responsibilities each file/module takes on.
  - e.g. If you need comments to separate sections within a file, it suggests the file or module has too many responsibilities.
- Minimize the responsibilities the project takes on.
  - If you know of an existing library or module that provides a more general solution to the problem at hand, suggest adopting it rather than implementing your own.
  - Especially if the task seems to require an disproportionately large amount of work, research on your own as needed to see whether a suitable library or module is available.
  - When choosing a library, consider whether its design would prevent compliance with the other rules.
- The directory structure, file names, class names, function names, variable names, and the structure of the code itself must be self-explanatory.
  - Do not use comments to explain what the code does.
  - Try not to use comments to explain why the code is like that.
  - You may use comments to cite sources, such as references or quotations, that justify design decisions.
- Prefer one-way data flow wherever possible.
  - Avoid implementing/using functions that mutate their arguments.
  - Avoid declaring global variables and accessing them from various places.
  - Avoid using the singleton pattern.
  - Avoid using refs across component boundaries.
- Prefer explicit data flow.
  - Avoid default parameter values.
- Do not commit dead code.
- Do not include non-ASCII characters anywhere in the code, including comments.
  - The exception is frontend code where non-ASCII characters are used for UI text.
    - e.g. UI text can be written in Japanese.
  - If you encounter Japanese or any other non-English language during this process, translate it into English.
    - The exception above also applies to this item.
        - e.g. Japanese UI text does not need to be translated into English.
        - e.g. new UI text should be written in Japanese when explicitly requested or when the existing UI text is already in Japanese.
